# arstro.device_manager.implement

**What it is.** Machines run Arstro Remote with the `relay` module; it keeps an outbound
WebSocket to the device manager. The device manager lists them; a viewer (browser or the
Python client) opens a channel to one, proves the machine's **access key** in a handshake,
and then reaches any `127.0.0.1:<port>` of it as HTTP, WebSocket or raw TCP. The device manager
only forwards ciphertext. Read `docs/relay/RELAY.md` (why + security model) and
`docs/relay/PROTOCOL.md` (wire format) once per session.

It is part of the Arstro Remote project: everything in `arstro.embedded_server.implement`
applies too (requirements first, every controller, logging, tests, A/B deploy, commit + push).
This skill adds the rules for the device manager.

**Changing the protocol:** edit `e2e.py` first (tables, constants, crypto), regenerate
`vectors.json`, update `PROTOCOL.md`, then the four implementations (relay server, browser
`e2e.js` / `sw.js` / `shim.js`, `agent.py`, `client.py`), then `AGENT_API.md`. A change of the
handshake, the key derivation or the frame format bumps `VERSION` (`LABEL` = `arstro-relay/<v>`)
and must keep refusing old peers with a clear error.

1. **Requirement** in § RLY (new ID or edited text), as in the embedded-server skill.
2. **Definition first** if the protocol changes (above), then the code.
3. **Tests**: `python3 server/tests/test_relay.py`, `python3 server/tests/test_relay_docs.py`,
   `python3 relay/tests/test_relay_server.py`, `node relay/tests/e2e_vectors.mjs`, and for viewer
   changes the full stack: run a relay + a test instance and
   `RELAY_URL=… DEVICE_ID=… DEVICE_KEY=… DEVICE_PORT=… ARSTRO_TOKEN=… node relay/tests/web/viewer_test.mjs`.
4. **Docs**: every row of the sync table that the change touches; `python3 scripts/req_coverage.py --check`.
5. **Image**: `docker build -f relay/Dockerfile -t arstro-devices:<version> .` (bump
   `relay/arstro_relay/__init__.py __version__`); restart the local device manager container
   and check `B/api/health` and the list.
6. **Machine side**: deploy into the idle A/B slot (`arstro.embedded_server.deploy`).
7. **Commit + push** (from the board, see the embedded-server skill and repo policy).

## Security rules (never relax without the user's explicit decision)

- The device manager never sees the key, never decrypts, never logs forwarded content.
- The viewer checks the **machine's** proof before sending anything derived from the key.
- Seal + send is one atomic step per channel (one lock in Python, one promise chain in JS):
  the nonce counter order must equal the wire order. Same for receive + open.
- The machine connects only to `127.0.0.1` / `[::1]`, honours the allow-list, keeps the limits.
- Never log or publish (topic, ops other than `relay.key` / `relay.rotate`, errors) the key,
  the join token or the device secret; `test_relay.py` checks the topic.
- Browser keys stay non-extractable; the raw key text is never stored.
- Keep `RELAY.md`'s security model honest: the browser viewer trusts the files the device
  manager serves; say so whenever the viewer changes.

## Gotchas

- `shim.js` runs everything in ONE function scope: a new feature's `function finish()` silently
  replaced the WebSocket code's `finish()` (sockets closed with 1006). Put new parts in their own
  closure (`const Transfers = (() => { ... })()`), as the Transfers panel is.
- Headless Chrome denies downloads unless allowed **per browser context**
  (`Browser.setDownloadBehavior` with `browserContextId`): a "canceled at 0 bytes" download in a
  test is that, not the code.

- The production device manager is behind an nginx that does NOT pass WebSockets (HTTP/1.1,
  default buffering, 60 s read timeout, ~1 MB bodies): everything must work over the HTTP
  transport. Test changes through `relay/tests/nginx_proxy.py`, not only directly.
- Browsers have 6 HTTP/1.1 connections per host and each pipe needs up to 2: one channel per
  device per browser (the shim's WebSockets ride the service worker's channel).

- Service workers and WebCrypto need a secure context: https, or `http://localhost`. A LAN
  address over plain http does not work for the browser viewer (the client does).
- A service worker cannot set real cookies or hand compressed bodies to the page: the worker
  keeps a cookie jar and the machine asks for `Accept-Encoding: identity`.
- Navigations to absolute paths outside `B/` are not seen by the worker: the shim rewrites
  links, iframes, forms and `window.open`; a page that builds such URLs some other way escapes.
- The relay forwards whole WebSocket messages; keep frames ≤ `MAX_MESSAGE` (DATA ≤ `CHUNK`).
- Port 8080 on the dev PC is taken by another tool: the PC's own Arstro Remote uses 8180.
- A viewer test run makes wrong-key attempts on purpose; more than five in 60 s lock the device
  for a minute - leave a minute between runs.
- Servers that refuse chunked uploads (Arstro answers 411): viewers always send `Content-Length`.
- The dev PC runs the device manager as the container `arstro-devices` (port 8090, volume
  `arstro-devices`); after changing `relay/` rebuild the image and recreate the container.
