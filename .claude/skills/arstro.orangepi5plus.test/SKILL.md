# Testing OrangePi5PlusController

Every test names the requirement IDs it proves; results are reported **per requirement**.
Start from `docs/requirements.md` and `docs/traceability.md` (generated by
`python3 scripts/req_coverage.py`, which also lists requirements without any test).

## Suites

| Suite | Where it runs | Proves | Command |
|---|---|---|---|
| `server/tests/test_daemon.py` | on the Pi, server running, desktop on `:0` | protocol, stats, shells, input, Wi-Fi, admin, socket | `cd ~/arstro-remote-src/tests && DISPLAY=:0 XAUTHORITY=~/.Xauthority python3 test_daemon.py` |
| `server/tests/test_sync_web.py` | on the Pi | sync between controllers, web/REST/WS, password, open mode, CLI local + remote | `python3 test_sync_web.py` |
| `server/tests/test_recorder.py` | on the Pi (switches to the test pattern and back) | preview H.264, recording, settings, conversion, gallery, guards | `python3 test_recorder.py` |
| `server/tests/web/ui_test.mjs` | any machine with Chrome + Node | the web UI end to end (login, all views at 4 sizes, preview, record, gallery, shells, touchpad) | `cd server/tests/web && npm install && ARSTRO_URL=http://<pi>:8080/ ARSTRO_TOKEN=<password> node ui_test.mjs [--shots DIR] [-k name]` |
| `app/test/*.dart` | any machine with Flutter | codec, terminal dedupe, every screen at 5 sizes incl. the Recorder | `cd app && flutter analyze && flutter test` |
| `app/test/reconnect_live_test.dart` | with a live server through the tunnel | link cuts, byte-exact shell resume | `ARSTRO_TCP=127.0.0.1:7788 flutter test test/reconnect_live_test.dart` |
| `server/tests/test_repo_policy.py` | anywhere | no environment values / secrets in the repo | `python3 server/tests/test_repo_policy.py` (add `ARSTRO_POLICY_WORDS=user,ssid,...`) |
| `scripts/check_scripts.sh` | anywhere | setup/build scripts (syntax, help, paths) | `scripts/check_scripts.sh` |
| `server/tests/bt_pairing_security_test.sh` | a Linux PC with Bluetooth near the Pi | pairing window, untrusted devices refused | see the script header |

`-k NAME` runs one test, `--list` shows tests and their requirements (Python and Node suites).
Pass the password with `ARSTRO_TOKEN` read at run time (e.g. over SSH from
`~/.config/arstro-remote/web_token`), never write it into files.

## Order for a full check

1. Cheap, local: repo policy, scripts, `flutter analyze`, `flutter test`,
   `python3 scripts/req_coverage.py --check`.
2. Deploy (`scripts/setup_pi.sh user@<pi>`), then on the Pi: `test_daemon.py`,
   `test_sync_web.py`, `test_recorder.py`.
3. Browser suite against the Pi (and `ARSTRO_URL_SECURE=http://127.0.0.1:<port>/` through an SSH
   tunnel for the WebCodecs path).
4. App on a device (below): Recorder live picture, record/stop, gallery thumbnail + playback,
   download, convert, delete; other tabs.
5. Manual items listed in `docs/traceability.md` (Bluetooth pairing, reboot, walk out of range).

## The app on a real Android device

* Over Bluetooth: pair in the pairing window (`arstro-remote pair`), then use the app normally.
* Without Bluetooth (device out of range, CI): `scripts/dev_tunnel.sh up user@<pi> SERIAL` - it
  forwards the control socket (7788) and the web port (8080) via `adb reverse`; in the app use
  *Connect by Bluetooth address…* → `tcp:127.0.0.1:7788`.
* Drive and check it with `scripts/adb_ui.py` (`dump`, `tap "<regex>"`, `xy X Y`, `shot NAME`,
  `wait`). Always pass the serial (`ANDROID_SERIAL=...`) and **never touch other adb devices**.
* Downloads land in `Download/Arstro/`; check with
  `adb shell content query --uri content://media/external/downloads --projection _display_name:_size`.

## Without the Pi: local test-pattern server

The server runs on a Linux PC with a test source (x264 replaces the Pi's VPU for the preview;
H.265/H.264 hardware targets show as unavailable, RAW and FFV1 work). Keep it sandboxed:

```bash
SB=<scratch dir>/sandbox; mkdir -p $SB/{config/arstro-remote,state,cache,run,videos}; chmod 700 $SB/run
printf '{"web_port": 18088}\n' > $SB/config/arstro-remote/config.json
printf '{"storage": "%s", "mode": "raw"}\n' "$SB/videos" > $SB/config/arstro-remote/recorder.json
export ARSTRO_SOCKET=/tmp/<short>.sock XDG_CONFIG_HOME=$SB/config XDG_STATE_HOME=$SB/state \
       XDG_CACHE_HOME=$SB/cache XDG_RUNTIME_DIR=$SB/run
cd server && env -u DISPLAY python3 -m arstro_remote run --no-bluetooth --simulate 1280x720@30   # background
```
`env -u DISPLAY` keeps it from moving your own mouse. Needs `python3-psutil`, GStreamer with
`x264enc`. For the app: a TCP→unix bridge on 127.0.0.1:7788 (the daemon only listens on the
unix socket) plus `adb reverse tcp:7788 tcp:7788` and `tcp:18088 tcp:18088`. Afterwards stop
the processes by PID and delete the sandbox recordings.

## Safety rules while testing

- The recorder suites use the test pattern; don't stress the real HDMI input (the board has
  reset under heavy HDMI load). Tests restore settings/source; if a run is killed, check
  `rec source` and `rec settings` (storage!) and restore them.
- The Wi-Fi tests never disconnect the Pi (it may be your only link). `wifi_live_reconnect` runs
  only with `--wifi-live` and a watchdog.
- The password tests change the password temporarily and restore it in `finally`; if a run
  was killed, check `arstro-remote web` still accepts the user's password.
- Headless Chrome does not repaint background tabs (xterm stays stale): `bringToFront()` before
  reading a page. Flutter: `scrollUntilVisible`/`pumpAndSettle` hang while the record button
  animates; restore `FlutterError.onError` (the `ErrorLog`) before any failing expect.

## Reporting

Report like this, then the failures with their messages and what you did about them:

```
Server (Pi): test_daemon 19/19, test_sync_web 13/13, test_recorder 10/10
Web UI: 10/10     App: flutter test 26/26, device check: Recorder/Gallery OK
Requirements: all covered except <IDs> (manual: <IDs> not done - why)
```
Never report a suite as passing that did not run; say which ones were skipped and why.
